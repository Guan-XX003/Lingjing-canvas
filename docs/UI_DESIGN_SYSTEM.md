# 万卷灵境 UI 设计系统修复准则

本文件记录本轮 UI 修复的目标和约束。后续代码修改应优先使用这些语义规则，而不是继续追加零散颜色覆盖。

## 设计目标

- 产品气质：生产工具优先，清楚、稳定、完成度高，避免营销页式装饰。
- 色彩偏好：使用清晰、可识别的语义色，但控制面积和饱和度；参考成熟设计系统的角色色管理，避免整屏发灰、发蓝或发艳。
- 按钮风格：2D 面片为主，使用明确边框和轻微投影，不使用大面积模糊光晕。
- 选中态：选中态必须稳定，鼠标悬停、聚焦、按下时不能丢失或切换成另一套状态。
- 危险操作：所有删除、移除、清空、重置等破坏性动作固定使用红色体系；常驻文字按钮使用浅红底、红边、红字，纯图标按钮默认只保留红色图标和轻边界，确认删除等最终破坏动作才使用实心红。
- 石墨灰主题：整体应是中性石墨灰，不偏蓝；天蓝色只作为清晰点缀和状态反馈，不铺满面板。

## 语义状态

- 默认按钮：中性面片、清晰边框、文字对比充足。
- 悬停按钮：只轻微提高亮度、边框和文字对比，不改变语义色。
- 选中按钮：使用主题主色实色面片，白色文字，稳定边框。
- 主要按钮：使用主题主色实色面片，可以比选中态稍强。
- 危险按钮：文字按钮默认使用 `--wj-danger-control-*` 的浅红底、红边、红字；纯图标危险按钮使用 `--wj-danger-icon-*`，控制红色面积，任何主题下不随主题色改变；只在确认弹窗主按钮等最终破坏动作中使用 `--wj-danger-bg` 实心红。
- 收藏/提示类功能按钮：使用 `--wj-favorite-*` / warning 语义色，小面积表达状态；不要混入普通选中态，也不要被全局 `aria-pressed` 规则染成主题主色。
- 禁用按钮：降低文字和边框对比，但仍保留可识别边界。
- 主题 accent 与操作 action 分离：`--wj-accent` 用于装饰、焦点和弱反馈；`--wj-action-*` 是选中和主要操作的上游语义色；`--wj-control-selected-*` / `--wj-control-primary-*` 只消费 action 变量，可以比 accent 更深以保证白字对比。

## 主题色

- dark：冷深色可以保留轻微蓝感，但按钮和边界要清楚。
- graphite：背景、面板、边框全部使用中性灰阶；主色为天蓝色。
- light / mist-blue / chrome-blue：保留浅色清爽感，避免低对比灰字。
- chrome-rose：粉色只作为主题主色，不让大面积控件发粉发糊。
- chrome-sand / warm-light：暖色主题保留暖感，但危险色仍为红。
- chrome-teal / sage-green：绿色主题使用独立绿系背景和边界层级，不继承浅色主题的蓝/珊瑚氛围；正绿色只用于选中态、主动作和关键反馈。

## 实现原则

- 优先补齐统一 CSS 变量，再让现有组件类接入变量；保留必要的旧类名匹配器，但输出颜色应走语义变量。
- 新增或调整主题时，先改 `--wj-action-bg`、`--wj-action-hover-bg`、`--wj-action-border`、`--wj-action-text`、`--wj-action-shadow`，再让选中态和主按钮自然继承，避免直接在各组件里硬写 selected/primary 颜色。
- 面板、输入框、折叠按钮、筛选组、收藏按钮和菜单分别使用 `--wj-panel-*`、`--wj-field-*`、`--wj-disclosure-*`、`--wj-filter-*`、`--wj-favorite-*`、`--wj-menu-*`；不要在项目分组弹窗、设置卡片、资源筛选、右键菜单里继续硬写局部背景、边框和阴影。
- 顶部导航、资源工具栏、设置侧栏等全局框架层使用 `--wj-chrome-*`；主导航文字、选中线和兼容旧入口使用 `--wj-nav-*` / `--wanjuan-nav-*`，不要再分别给这些区域硬写灰蓝渐变。
- 画布控件和连线使用 `--wj-canvas-control-*`、`--wj-edge-*`、`--wj-loading-node-*`；不要再在 React Flow 控件、运行连线、加载节点里按主题硬写颜色。
- 收藏星标、资源卡收藏和会员等级徽章/图标使用 `--wj-favorite-*`、`--wj-tier-*`；不要在模型列表、资源管理或会员设置中继续硬写黄、紫、蓝。
- 减少 `nth-child`、硬编码 hex、只针对某张截图的选择器。
- 对已有类名做语义化桥接，例如 active、aria-pressed、data-active、danger。
- Electron 注入层只做最终桌面一致性兜底，核心规则放在 renderer 样式文件。
- 每个阶段本地提交，不经用户确认不推送远端。
